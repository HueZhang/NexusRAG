## ADR-000 · 采用"通用中台 + 可插拔场景模板"架构

- 日期：2026-11-24
- 状态：已采纳
- 背景：目标是"好找工作"的 RAG 作品；单做一个应用天花板低、不可复用；纯做框架又难 demo。
- 选项：
  - A. 只做一个医疗 RAG 应用 —— 简单，但故事窄、复用性差。
  - B. 通用中台 + 场景模板 —— 有平台叙事、可复用，架构稍复杂。
- 决策：B。核心层只面向接口，场景以 Adapter 插入，医疗作为首个模板。
- 理由：平台叙事是简历最大亮点；"换行业只换模板"体现架构能力。
- 代价 / 风险：前期抽象成本；需克制过度设计，避免"为分层而分层"。

## ADR-001 · 主语言选 Python（而非 Java/C#）

- 日期：2026-11-24
- 状态：已采纳
- 背景：RAG 主链路生态、目标岗位需求、个人时间（在职 3–4 月）。
- 选项：
  - A. Python 全栈 —— RAG 生态最全、岗位多、能快速出成果。
  - B. Java + Python 混合 —— 简历可写 Java，但双栈维护成本高、在职难做深。
  - C. 纯 Java（Spring AI）—— RAG 生态弱、JVM 八股必考。
- 决策：A，Python 为主；Java 作为"可迁移能力"而非项目主打。
- 理由：3–4 个月要出可展示成果，双栈会都做不深；RAG 瓶颈主要在模型 IO 与并发/摄取，
  非语言性能，Python 完全够用。
- 代价 / 风险：少部分 Java 岗不匹配；需在面试中说明"可快速上手 Java 栈"。
